HISTORY_RETENTION  (always)
  Historical transactions are whatever the node kept
  blind: getTransaction returns null outside the node’s retention window. Public mainnet endpoints commonly retain on the order of days, not the chain’s full life, and the window is a BigTable/leader configuration Dot cannot read. A program whose integrators were busy in 2024 can show a small graph today because the 2024 traces are gone, not because nobody called it.
  out:   Run Dot continuously so the graph is built while the traces are still hot and persisted in Dot’s own store. For backfill, use a provider archive node, or `getBlock`/`getBlocks` streaming into your own indexer, or Yellowstone gRPC `subscribe` on transaction notifications, which is a live feed rather than a historical read.

NO_CHAIN_WIDE_UPGRADE_SUBSCRIPTION  (always)
  Core JSON-RPC has no "every bytecode change" feed
  blind: There is no `getProgramChanges` and `subscribe*` is per-account. Watching the whole upgradeable loader means polling `getProgramAccounts` on a program that owns >100k accounts, which providers gate, rate-limit or reject outright.
  out:   Dot ships both layers: `watch --targets` polls a named list over JSON-RPC, and `watch --yellowstone <url>` subscribes by owner over Geyser and sees every `ProgramData` write on the cluster. The gRPC feed costs zero JSON-RPC calls, which is what makes chain-wide detection budget-feasible at all.

GRPC_LIVE_PATH_UNVERIFIED  (when triggered)
  The Geyser path is typechecked and unit-tested, but was not run against a live endpoint
  blind: The subscription request, the account-update decoding and the classification logic in `src/rpc/yellowstone.ts` were written against the generated types of `@triton-one/yellowstone-grpc` 9.0.1 and exercised with an injected fake stream. No Geyser endpoint was reachable in the session that built it, so handshake, auth-token handling and replay semantics are unverified in the field. Two of its field shapes already contradict the usual write-ups (owner/account are base58 strings, not bytes; lamports/writeVersion are decimal strings), which is what to expect of a layer nobody has poked at.
  out:   Run `dot watch --yellowstone <url>` against a real endpoint and check `feed.statsView()`: `updates` should rise, `startupSkipped` should be non-zero on a replay, `layoutMismatch` should stay near zero. Treat a flat `updates` counter with no error as the signature of a filter that matches nothing, not as an idle chain.

PROGRAMDATA_REVERSE_LOOKUP  (when triggered)
  A ProgramData write does not say which program it is
  blind: Geyser reports the account address; `find_program_address` is one-way, and nothing on chain stores the reverse pointer. On a fresh daemon most `ProgramData` accounts therefore arrive nameless, and a nameless upgrade cannot be put in a graph.
  out:   `ProgramIndex` resolves it three ways, cheapest first, and stamps the method on the answer: pointer accounts the feed already saw (free), the writing transaction plus local PDA re-derivation (one call, exact), or a reverse `getProgramAccounts` scan (heavy, commonly gated). Events that resolve to none are **counted and skipped** (`unresolved`), never guessed and never silently dropped.

BLOCK_FETCH_AMPLIFICATION  (when triggered)
  Block batching buys calls with bandwidth, not with cost
  blind: One `getBlock` replaces many `getTransaction` calls, so the RPC-call ceiling stops binding — and the payload becomes every transaction in the slot, most of them unrelated to the target. On a busy program the byte count goes up by two or three orders of magnitude while the call count drops by one. A tool that reports only the first number is recommending the more expensive option.
  out:   Dot plans against an explicit cost model, prints both sides of the trade in the report (`callSavingRatio`, `byteAmplification`), and refuses a block above `maxBlockBytes`. Run `dot calibrate --rpc <url>` to replace the labelled defaults with sizes your endpoint actually serves; until then the rationale string says `defaults_unverified`.

ENDPOINT_CORROBORATION  (when triggered)
  Corroboration is only meaningful at the same slot
  blind: Two endpoints holding different bytes for one account at different slots are describing chain progress, not contradicting each other. And when one endpoint is down, the surviving number is uncorroborated rather than wrong.
  out:   `ResilientClient` compares only same-slot reads and splits the outcomes: `agreed`, `disagreed` (halt, P0 with `tierSource: integrity`), `slot_mismatch` (inconclusive, continue), `single_source` (continue, labelled), `both_failed` (halt, no conclusion). Every report carries the verdict, not just the ones that halted.

FEED_BACKPRESSURE  (when triggered)
  A deploy storm drops analyses, with a count
  blind: When the chain-wide feed fires faster than the daily RPC pool allows, events are dropped. Dropped is not the same as clean, and a daemon that dropped forty upgrades looks identical to one that saw none.
  out:   `UpgradeDispatcher` caps each investigation at `--per-event-rpc` (default 50) and the daemon at `--daily-rpc`, serves authority handovers and vanished ProgramData ahead of routine bytecode writes, drains serially so a burst cannot turn into a thundering herd, and exposes `dropped: {queue_full, daily_pool, below_minimum}`. Below `minViable` calls an analysis is refused rather than run thin.

CPI_DEPTH_ATTRIBUTION  (always)
  innerInstructions is flat; depth is inferred, never given as a tree
  blind: `meta.innerInstructions[i]` maps a group of CPI instructions onto one outer instruction index, and the list inside the group has no parent pointers. At CPI depth >= 3 the caller of a nested call is not recoverable from the group alone. Measured on mainnet, instructions do carry `stackHeight` and `meta.logMessages` carries `Program <id> invoke [N]`, and Dot uses both — but `stackHeight` is absent from `@solana/web3.js` v1 type declarations and is not guaranteed by every node, and the log collector truncates.
  out:   Dot reports `attributionQuality`: `stackHeight` (exact), `logs` (exact, truncation-bounded) or `flat` (upper bound only, nested callers credited to the top-level program). For guaranteed depth-agnostic capture, parse a Yellowstone gRPC transaction stream, or record with an instrumented validator, since neither depends on the RPC’s log caps.

PARSED_INSTRUCTION_ACCOUNTS  (when triggered)
  Instruction accounts are pubkeys in jsonParsed and indexes in json — and parsed instructions have neither
  blind: Three shapes coexist in one response. A partially-decoded instruction under `encoding: "jsonParsed"` carries `accounts` as base58 pubkeys already resolved; the same field under `encoding: "json"` carries integer indexes into static keys followed by loaded-writable then loaded-readonly; and a *parsed* instruction (`spl-token`, `system`, …) carries no `accounts` at all, only whatever pubkeys happen to appear inside `parsed.info` under inconsistent names (`source`, `destination`, `newAccount`, `owner`, …). A parser that assumes one shape does not crash on the others — it reads `keys["6tv7sUQ4…"]`, gets undefined, and reports that no value moved. That is how a blast-radius tool produces a confident zero.
  out:   Dot accepts both entry types, resolves them through one table (`src/graph/keys.ts`), tags every frame `accountSource: accounts | parsed_info | none`, and records pubkeys that appear in an instruction but not in the key table as an anomaly instead of guessing. `test/graph.test.ts` asserts the two encodings of the same trace yield the same graph.

WEB3JS_JSONPARSED_VALIDATOR  (when triggered)
  @solana/web3.js v1 cannot deserialize its own jsonParsed inner instructions
  blind: Not a limit of the chain but of the client, and it is the reason Dot owns its JSON-RPC layer: `Connection.getTransaction(sig, {encoding: "jsonParsed", maxSupportedTransactionVersion: 0})` throws `StructError: At path: meta.innerInstructions.0.instructions.0.accounts -- Expected an array value, but received: undefined` on real CPI-heavy mainnet transactions, because the schema requires `accounts` on parsed instructions the node does not send it on. Anything that trusts those types silently inherits the crash — or worse, a catch block that turns it into "no dependencies found".
  out:   Call the RPC directly and parse against Dot’s own wire types (`src/rpc/wire.ts`), which model `accounts` as optional and `stackHeight` as present-but-optional. Reproduced 2026-10-21 against api.mainnet-beta.solana.com with @solana/web3.js 1.99.x.

NO_IDL_CONTRACT  (always)
  No IDL, no semantic claim
  blind: There is no mandatory on-chain IDL. Anchor programs may or may not publish one, the legacy `anchor:idl` PDA is version- and size-dependent, and non-Anchor programs frequently ship a binary with no interface at all. In `mode: real` the model then has nothing to read, and Dot must say so instead of paraphrasing a bytecode diff.
  out:   `--idl <path|url>` to supply a published IDL and a prior version for a real diff. Without it, `narrative.refused = "idl_unavailable"` appears in the report and the tier rests only on posture plus observed graph.

VALUE_IS_PROXY  (always)
  Value routed is an upper-bound proxy, per transaction, not per edge
  blind: Lamports move between accounts; nothing in the response says "this transfer belongs to this CPI leg". Dot sums positive balance deltas over the accounts a call touched, and takes token deltas from pre/postTokenBalances, which are per-transaction arrays. A swap through a router that touches six accounts is counted once on the receiving side, and cannot be split into legs.
  out:   Treat it as a ranking signal. For a settlement-grade number you need an account-level state diff per instruction, which means an instrumented node or an indexer that stores instruction-level balance changes.

PDA_HOLDINGS_NOT_ENUMERATED  (always)
  Program-held vaults are not enumerated
  blind: TVL sitting in a program’s PDAs is not visible from the transaction sample. There is no RPC that lists "all token accounts owned by these PDAs"; `getTokenAccountsByOwner` takes one owner at a time and `getProgramAccounts` on the token program with an owner filter is a full-program scan providers will not serve.
  out:   Compute vault balances from a known-PDA list (the IDL or the deployment repo gives you the seeds) via `getMultipleAccounts`, or use an indexer/DAS API. Dot leaves `blastRadius.lamportsRouted` explicitly labelled as routed-through value, not custody.

FAILED_TRANSACTIONS_ROLLED_BACK  (when triggered)
  A failed transaction moved nothing
  blind: Inner instructions are still populated for the part of a transaction that executed before it failed, and a CPI that fails inside a successful transaction is rolled back to its checkpoint. Counting those as interactions is right; counting them as value moved is not.
  out:   Dot keeps `failedCpiOccurrences` and `tracesFailed` separate from the value sums, so an integrator that started erroring on the new bytecode shows up as a signal rather than as volume.

SIGNATURE_INDEX_IS_KEY_BASED  (always)
  getSignaturesForAddress matches keys, not roles
  blind: The index returns any transaction where the address appears as an account key: as the invoked program, as a CPI target, as a mint, as a PDA, as a token account. For an id that is also a commonly-referenced account, the sample fills up with transactions that have nothing to do with the program’s execution.
  out:   Filter on "appears as a program id in an instruction" during normalization, which Dot does by dropping frames whose program never actually ran. Sample size and `sampleCoverage` are reported so a reader can see how much of the window was noise.

ADDRESS_TABLE_RESOLUTION  (when triggered)
  v0 transactions need table-loaded addresses resolved before indexes mean anything
  blind: Instruction account indexes point into static keys followed by loaded writable then loaded readonly addresses. If a node omits `meta.loadedAddresses`, every index past the static table is wrong, and the graph is wrong in a way that looks like data rather than like an error.
  out:   Dot resolves both paths and reports `keys.method` plus any `unresolvedIndexes` as anomalies in the evidence ledger. Zero unresolved indexes is a precondition for trusting an edge.

NO_PRE_DEPLOY_ANALYSIS  (always)
  Dot sees landings, not intentions
  blind: A bytecode change that has not been written on chain does not exist for Dot: no propose-stage review, no repository, no CI signal. It is a runtime tool, deliberately not a static analyzer of what is about to be deployed.
  out:   Partly narrowed: the Geyser owner filter also catches the loader’s `Buffer` accounts, so `dot watch --yellowstone` prints a `STAGED` line when a program is being uploaded before it lands — an early trigger, not an analysis. Pair it with a static analyzer on the staged bytes.

FINALITY_VS_LATENCY  (always)
  Finalized-only means slow-only
  blind: Dot reads at `finalized` because a graph built on `processed` data can be reorged out from under it. That costs minutes of detection latency, which matters if the upgrade you are watching is being exploited right now.
  out:   `--commitment confirmed` trades reorg risk for latency. Do not use `processed` for a persisted graph.

SINGLE_NODE_TRUST  (always)
  One RPC node is one point of failure and one point of view
  blind: A provider can cache, filter, lag, or serve you a node that is behind. Every number in a Dot report is a statement about what one endpoint chose to return. A quiet blast radius can mean a filtered node.
  out:   `--secondary-rpc <url>` reads the `ProgramData` account from both endpoints and halts on a same-slot contradiction; each endpoint gets its own `Budget` so a retry on one cannot silently spend the other’s. `rpc.rpcErrorCodes` and `pruned` remain the first places to look.

NO_MALICE_DETECTION  (always)
  Dot ranks attention; it does not adjudicate guilt
  blind: Nothing here determines whether an upgrade is malicious. A P0 says "posture and blast radius justify a human before the weekend", and a P3 says "the evidence Dot could gather does not". Absence of a finding is not a clean bill of health, and the tier is a queue position, not a verdict.
  out:   Read the `components` array and the evidence ledger before escalating to anyone. If `cappedBy` is non-null, the tier is capped by a blind spot and the next step is a better data source, not a louder alarm.

P0: Stop-and-verify. An attributed blast radius plus a posture that could have pushed this unilaterally. Treat the upgrade as hostile until the operator says otherwise.
P1: Review today. Either the exposure or the posture is significant; a human should read the diff and notify integrators.
P2: Queue for review. Real change, bounded exposure, or a gap in what the node would return.
P3: Informational. Logged, aggregated, no action expected.
