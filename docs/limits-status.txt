BYTECODE_SCAN_BLIND_ON_COMPILED_IMAGES
  narrowed: The assumption was tested instead of asserted, it failed, and the failure is now repaired rather than documented. With the Solana toolchain on this box a compiled image holding ten `[u8; 8]` discriminators yields **0 of 10** contiguous selectors, and a program built with anchor-lang 0.30.1 yields **0 of 6** contiguous and 0 of 6 four-byte halves — the constants are split across a `mov32`+SBF-`hor64` immediate pair, or dissolved into a byte-wise compare tree. `src/state/sbfSelectors.ts` parses the ELF section table, walks `.text` as eBPF and recovers both shapes: **10 of 10** on the committed compiled fixture (all via the immediate pair), **6 of 6** on the anchor-lang 0.30.1 program (all via the compare chain), and **0 of 30** on names neither program implements — a candidate is reported only when it equals a hash the IDL supplied, so a misdecode costs a miss and never a false claim. `diffBytecode` now reports `structural` with a real entrypoint set on images where the old sweep returned nothing.
  remains: Two emission shapes are demonstrated; a compiler is free to choose others. A jump table or a binary search over `data[0]` would not produce the consecutive-compare run the compare-chain rule requires, and a `match` lowered onto values wider than a byte would drop out of the stream entirely — both then surface as "not located", capped by `confidence: "unscannable"`, not as an absent handler. The chain rule pairs the arm body (data[1..8]) with a leading-byte compare emitted ~87 instructions earlier by the outer switch, so a location there is an arm-plus-dispatch pair, not one contiguous test, and `via` is carried into the report to say so. One real anchor-lang program, six instructions, built locally: the numbers are not a corpus. A coverage study against deployed programs was attempted and could not be completed here: `node scripts/probe-coverage.ts` reads the ELF out of four live mainnet images (432 KB to 10.5 MB — the magic-at-45, no-length-prefix assumption holds on real deployed accounts, which that probe is the evidence for) and then finds no `anchor:idl` PDA on any of them, so the located/declared ratio is undefined for every program reachable from this box. The residual is therefore a corpus-access problem, not a decoder problem: naming more programs needs `getProgramAccounts` on the loader (gated on the public endpoints) or a supplied (program, IDL) list. Two images remain the honest claim until someone with that access runs it.
  fix:     npx vitest run test/bytecode.test.ts (uses test/fixtures/sbf-dispatch.so), or DOT_TEST_SO=program.so DOT_TEST_IDL=idl.json npx vitest run test/bytecode.test.ts for any real artifact. Wider coverage is a sampling job: run the gated check against published mainnet programs and report the fraction located. The corpus itself needs an index: `node scripts/probe-coverage.ts` is the sampling harness, but it can only name programs this box was given — widen it with `getProgramAccounts` on the loader from an endpoint that allows it, or a list of (program, IDL) pairs from a deployment you audit.
  !deviation from plan: The plan treated this item as "unvalidated, pending a toolchain", then as a named defect once the toolchain refuted the assumption. Both were under-described: the defect was in Dot's decoder, not in the bytecode. It stayed NARROWED when the fix landed because the fix is proven on two images, not on a corpus, and a taxonomy that gains RESOLVED as soon as code works is marketing — the residual is a claim about coverage, which is what NARROWED means here.
  tests:   test/bytecode.test.ts

BLOCK_FETCH_AMPLIFICATION
  not a code problem: A block contains every transaction in the slot. Dot prices this explicitly: the plan prints callSavingRatio and byteAmplification together, refuses oversized blocks, and only batches when calls genuinely bind. The inputs are now measured, not guessed — `docs/calibrated-model-2026-10-21.json` came out of `dot calibrate` against mainnet (506 tx/block, 18,040 bytes per fetched transaction) and `test/calibrate.test.ts` asserts the plan uses it.
  remains: No encoding choice makes a block smaller than the block. Bandwidth-bound backfills need a filtered feed or an indexer, not a better getBlock call. The measurement is one endpoint on one day: block sizes vary by an order of magnitude between slots, so a deployment should re-run calibrate against its own provider.
  fix:     dot calibrate --rpc <url> replaces the labelled defaults with your endpoint’s real sizes; --cost-model <file> or DOT_COST_MODEL supplies it.
  tests:   test/ingest.test.ts, test/calibrate.test.ts

NO_MALICE_DETECTION
  not a code problem: A tier is printed as a queue position with its components exposed, and every report ends with a sentence saying a low tier is a statement about evidence. Three signature axes now notice the *shape* of an attack — who funded the authority and when, whether the bytecode answers to a selector the published interface denies, whether the timing fits the program's own cadence — and when the gate is satisfied the report says SUSPECTED_MALICIOUS with the axis points, the gate and the evidence under it, above the fold in the markdown and in both watch summary lines.
  remains: None of that is intent. Dot ships no mixer list, so "funded from a suspect source" is only ever "funded from an address the operator named"; it cannot read a multisig threshold or a signer set's age; it has no incident feed; and a node's retention window caps how young it is allowed to call a wallet. The gate is a routing decision with a written-down reason, and the honest failure mode is symmetric: a team with a fresh ops wallet, a stale IDL and a benign upgrade produces the same signature as an attacker and will be screamed at. Deciding whether an upgrade is hostile still requires the repository, the governance discussion and who signed — none of which this tool reads.
  tests:   test/risk.test.ts, test/malice.test.ts, test/funding.test.ts, test/danger.test.ts
